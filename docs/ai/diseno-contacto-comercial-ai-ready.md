## 1. Por qué este documento

El North Star de SIVAN (v1.1, junio 2026) define la **Fase 0 (ahora → Q3 2026)** como
*"fijar el esquema de dato AI-ready (casi listo en ControlLocal)"*, y fija tres reglas que
gobiernan este diseño:

- *"El dato es el activo, no el código. Capturarlo estructurado **y etiquetado** desde hoy."*
- *"Medir el resultado es obligatorio desde el evento #1."*
- El moat es saber *"qué se cerró, a qué precio real, en cuánto tiempo, **por qué se cayó**."*

Consecuencia de diseño: la tabla de interacciones **no es trazabilidad operativa, es la materia
prima del moat**. Un `observaciones TEXT` libre no sirve para entrenar; lo que no se capture
etiquetado hoy es dato perdido (el North Star: *"cada mes sin dato es moat perdido"*).

Además el producto operará por **dos canales**: app web nativa y un **agente conversacional de
WhatsApp**. Eso obliga a separar el ruido conversacional del hecho comercial (§6).

## 3. La familia `ContactoComercial` (responde E.3)

**El contexto NO se resuelve con herencia.** Los cuatro contextos (prospección, captación,
oportunidad, solicitud) comparten *todos* sus atributos; lo único que varía es a quién apuntan.
Eso es asociación polimórfica, no subtipos. Subtipar por contexto daría 4 tablas idénticas.

**La herencia va por naturaleza del contacto**, donde sí hay atributos propios reales:

```
contacto_comercial  (supertipo)
   ├── interaccion          → sin columnas extra (llamada, correo, WhatsApp)
   ├── visita               → + nivel_interes, objecion_principal, opinion_precio, proxima_accion
   ├── oferta_negociacion   → + monto, origen, cadena de contraofertas          ★ NUEVO
   └── reporte_propietario  → + consultas, visitas, periodo (YA EXISTE en v1)
```

```sql
CREATE TABLE contacto_comercial (
    id_contacto      BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tipo_contacto    VARCHAR(15) NOT NULL,   -- INTERACCION|VISITA|OFERTA|REPORTE
    entidad_tipo     VARCHAR(30) NOT NULL REFERENCES entidad_tipo(codigo),
    id_entidad       BIGINT      NOT NULL,
    fecha_hora       TIMESTAMPTZ NOT NULL DEFAULT now(),   -- futura columna de partición
    canal            VARCHAR(1)  NOT NULL,
    resultado        VARCHAR(30) NOT NULL REFERENCES resultado_contacto(codigo),
    observaciones    TEXT,
    atributos        JSONB,                                 -- detalle variable, índice GIN
    id_rol_agente    BIGINT      NOT NULL REFERENCES detalle_agente(id_persona_rol),
    id_historial     BIGINT      REFERENCES historial_estado(id_historial),
    id_externo       VARCHAR(100),
    origen_sistema   VARCHAR(30) NOT NULL DEFAULT 'WEB',
    CONSTRAINT uq_contacto_externo UNIQUE (origen_sistema, id_externo)
);
CREATE INDEX ix_contacto_entidad ON contacto_comercial (entidad_tipo, id_entidad, fecha_hora DESC);
CREATE INDEX ix_contacto_agente  ON contacto_comercial (id_rol_agente, fecha_hora DESC);
```

- **`entidad_tipo` + `id_entidad`**: mismo patrón polimórfico que `historial_estado` ya usa en la v2
  (y que MEJ-19 pide unificar). Un contexto nuevo = fila en el catálogo, sin migración.
- **`id_historial`** (nullable): liga el contacto con la transición que provocó, **sin duplicar el
  estado**. `historial_estado` ya guarda `estado_anterior`/`estado_nuevo` → "qué cambió esta
  interacción" sale de un join. La dirección importa: el contacto conoce al historial, nunca al revés
  (el historial es universal y no debe conocer el módulo comercial).
- **`id_externo` + `origen_sistema` UNIQUE**: idempotencia de webhooks (el `wamid` de WhatsApp).
  Los webhooks reintentan por diseño; sin esto se duplica el timeline.
- **`resultado`** sale a catálogo (`resultado_contacto`), reemplazando el CHECK condicional de
  4 dominios de la v1, que era frágil y crecía con cada contexto.

**Rendimiento con JPA (`@Inheritance(JOINED)`)**: el **timeline lee solo el supertipo** (0 joins,
tiene todo lo común); el subtipo se carga únicamente al abrir el detalle. El caso frecuente es barato.

## 4. Captura AI-ready: los tres niveles del dato

El error a evitar es meter todo en un campo. Hay tres niveles y cada uno tiene su lugar:

| Nivel | Ejemplo | Dónde | Para qué |
|---|---|---|---|
| **Desenlace** | `PIDE_INFORMACION` | `contacto.resultado` (catálogo cerrado) | mueve estados, embudo, reportes |
| **Etiquetas** | `PIDE_DOCUMENTOS` + `OBJETA_PRECIO` | tabla **N:M** | recomendación de tareas, features de ML |
| **Matiz** | *"quiere ver los papeles antes de decidir"* | `observaciones` + `atributos` JSONB | RAG / contexto LLM (Fase 2) |

Una interacción puede tener **varias etiquetas a la vez** ("pidió documentos" *y* "objetó el precio"),
por eso es N:M y no una columna. Es también la única forma de cubrir la **cola larga** de objeciones
que un enum nunca abarca.

```sql
CREATE TABLE etiqueta_contacto (            -- catálogo (D-07: cerrado, se amplía revisando)
    codigo       VARCHAR(40) PRIMARY KEY,   -- PIDE_DOCUMENTOS, OBJETA_PRECIO, PIDE_REBAJA…
    familia      VARCHAR(20) NOT NULL,      -- CONSULTA | OBJECION | INTENCION | RIESGO
    descripcion  VARCHAR(200) NOT NULL,
    activo       BOOLEAN NOT NULL DEFAULT TRUE
);

-- Asignación VERSIONADA: una etiqueta puede resolverse o ser sustituida por nueva
-- evidencia sin borrar la clasificación anterior (trazabilidad del criterio del modelo).
CREATE TABLE contacto_etiqueta (
    id_contacto_etiqueta BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_contacto    BIGINT      NOT NULL REFERENCES contacto_comercial,
    codigo         VARCHAR(40) NOT NULL REFERENCES etiqueta_contacto,
    confianza      NUMERIC(3,2),            -- 0.00–1.00 cuando la puso un modelo
    origen         VARCHAR(10) NOT NULL,    -- HUMANO | REGLA | LLM
    estado         VARCHAR(12) NOT NULL,    -- ACTIVA | RESUELTA | SUSTITUIDA
    modelo_version VARCHAR(40),             -- qué modelo/prompt la produjo
    fecha_desde    TIMESTAMPTZ NOT NULL DEFAULT now(),
    fecha_hasta    TIMESTAMPTZ
);
CREATE INDEX ix_etiqueta_codigo ON contacto_etiqueta (codigo, id_contacto);
-- Una sola vigente por (contacto, etiqueta): índice único parcial.
CREATE UNIQUE INDEX uq_etiqueta_activa ON contacto_etiqueta (id_contacto, codigo)
    WHERE estado = 'ACTIVA';
```

> ⚠️ **Nota de diseño**: la PK no puede ser `(id_contacto, codigo)` como se planteó inicialmente,
> porque el versionado permite que la misma etiqueta se reasigne tras ser sustituida. Se usa PK
> surrogate + **índice único parcial** sobre las vigentes, que es el mismo patrón que ya usa
> `uq_captacion_activa_por_local` en V5.

**`origen` + `confianza` + `modelo_version` no son adorno**: son la gobernanza auditable que el
North Star pone como sello frente al *agent washing*. Permiten (a) saber qué etiquetó la IA y qué
corrigió una persona, (b) entrenar filtrando por validación humana, y (c) **reevaluar el histórico
cuando cambie el modelo** (por eso `modelo_version`).

### 4.1 Clasificación autónoma por umbral (D-06 revisado)

El etiquetado **no requiere aprobación humana previa** — sería fricción incompatible con un canal
conversacional. El control es por umbral de confianza:

| Confianza | Comportamiento |
|---|---|
| **≥ 0.80** | Etiqueta activa y utilizable para acciones |
| **0.60 – 0.79** | Se almacena con baja confianza; **no habilita acciones irreversibles** |
| **< 0.60** | No se asigna |

Las etiquetas **evolucionan solas con nueva evidencia**, sin borrar el histórico:

```
Primera inferencia:      RIESGO_IDENTIDAD_NO_VERIFICADA   estado=ACTIVA
Luego valida documento:  RIESGO_IDENTIDAD_NO_VERIFICADA   estado=RESUELTA, fecha_hasta=now()
```

El humano-en-el-loop pasa de ser **bloqueante** (aprobar antes) a **correctivo** (corregir después,
`origen=HUMANO`). La supervisión humana del North Star se conserva donde importa —decisiones
comerciales y legales— no en el etiquetado.

### 4.2 Set inicial: 28 etiquetas en 4 familias (D-15)

Las etiquetas describen **lo que aparece en la conversación**. Los desenlaces comerciales siguen
viviendo en `resultado_contacto` — no se mezclan.

| Familia | Etiquetas |
|---|---|
| **CONSULTA** (7) | `CONSULTA_PRECIO`, `CONSULTA_DISPONIBILIDAD`, `CONSULTA_UBICACION`, `CONSULTA_AREA_DISTRIBUCION`, `CONSULTA_CONDICIONES_CONTRATO`, `CONSULTA_DOCUMENTACION`, `CONSULTA_SERVICIOS_GASTOS` |
| **OBJECION** (8) | `OBJECION_PRECIO`, `OBJECION_GARANTIA_ADELANTO`, `OBJECION_COMISION`, `OBJECION_UBICACION`, `OBJECION_AREA_DISTRIBUCION`, `OBJECION_ESTADO_LOCAL`, `OBJECION_PLAZO_CONTRATO`, `OBJECION_DOCUMENTACION` |
| **INTENCION** (8) | `INTENCION_SOLICITA_FOTOS_VIDEO`, `INTENCION_SOLICITA_DOCUMENTOS`, `INTENCION_AGENDAR_VISITA`, `INTENCION_REPROGRAMAR_VISITA`, `INTENCION_NEGOCIAR`, `INTENCION_ENVIAR_PROPUESTA`, `INTENCION_RESERVAR`, `INTENCION_POSTERGAR` |
| **RIESGO** (5) | `RIESGO_IDENTIDAD_NO_VERIFICADA`, `RIESGO_POSIBLE_DUPLICADO`, `RIESGO_DATOS_INCONSISTENTES`, `RIESGO_POSIBLE_FRAUDE`, `RIESGO_DOCUMENTACION_PENDIENTE` |

**Lo que NO es etiqueta** (sigue en `resultado_contacto`): `VISITA_AGENDADA`, `NO_RESPONDIO`,
`PROPUESTA_ENVIADA`, `NEGOCIACION_INICIADA`, `DESCARTADO`, `CIERRE_REALIZADO`.

Ejemplo de una interacción bien clasificada:

```
resultado:  VISITA_AGENDADA
etiquetas:  CONSULTA_PRECIO · OBJECION_GARANTIA_ADELANTO · INTENCION_SOLICITA_DOCUMENTOS
```

> ⚠️ **Revisar la familia RIESGO antes de implementar**: 4 de sus 5 códigos no son hechos de la
> conversación sino **estados de la entidad** (`RIESGO_IDENTIDAD_NO_VERIFICADA` y
> `RIESGO_POSIBLE_DUPLICADO` son de la persona; `RIESGO_DOCUMENTACION_PENDIENTE` es de la
> solicitud). Modelarlos como etiqueta obliga a un join a `contacto_etiqueta` para responder
> "¿qué clientes están sin verificar?", cuando debería ser un `WHERE` sobre una columna de
> `persona`. Recomendación: dejar en la familia solo `RIESGO_POSIBLE_FRAUDE` (que sí se observa en
> el mensaje) y derivar el resto de columnas de estado. Ver §12.

**Curación (D-07)**: el LLM solo puede usar etiquetas existentes. Lo que no encaja cae en
`observaciones` y se revisa periódicamente para decidir si merece etiqueta nueva. Esto evita la
fragmentación (`PIDE_DOCS` vs `PIDE_DOCUMENTOS`) que rompería la comparabilidad histórica.

## 5. Negociación con contraofertas (nuevo — no existe en la v1)

La v1 **no modela negociación**: `solicitud_alquiler` guarda un único `monto_propuesto` y una
`fecha_vigencia_oferta`. No hay rondas ni contraofertas. Es funcionalidad nueva, así que **no la ata
el contrato congelado**.

```sql
CREATE TABLE oferta_negociacion (
    id_contacto        BIGINT PRIMARY KEY REFERENCES contacto_comercial,
    monto_ofertado     NUMERIC(12,2) NOT NULL,
    moneda             VARCHAR(3)  NOT NULL DEFAULT 'PEN',
    origen             VARCHAR(1)  NOT NULL,   -- C=cliente, P=propietario   (D-04)
    id_oferta_anterior BIGINT REFERENCES oferta_negociacion,   -- cadena de contraofertas
    ronda              SMALLINT    NOT NULL,
    estado             VARCHAR(1)  NOT NULL,   -- P pendiente, A aceptada, R rechazada, C contraofertada
    plazo_meses        INT, meses_garantia INT, meses_adelanto INT,
    vigencia_hasta     DATE,
    CONSTRAINT ck_oferta_origen CHECK (origen IN ('C','P')),
    CONSTRAINT ck_oferta_monto  CHECK (monto_ofertado > 0)
);
```

La **self-FK `id_oferta_anterior`** da la trazabilidad completa como cadena; `ronda` denormalizado
evita recorrerla para saber en cuál se va (O(1)).

**El agente es siempre el autor (D-04)**: `contacto_comercial.id_rol_agente` es NOT NULL y siempre
es el agente; `origen` (C/P) registra de parte de quién viene la propuesta. No hace falta modelar al
cliente y al propietario como autores.

**Monto histórico (D-05)** — en `solicitud_alquiler`:

```sql
monto_propuesto    NUMERIC(12,2) NOT NULL,   -- INMUTABLE: la oferta original
monto_vigente      NUMERIC(12,2) NOT NULL,   -- caliente: última ronda vigente
id_oferta_vigente  BIGINT REFERENCES oferta_negociacion,
ronda_actual       SMALLINT NOT NULL DEFAULT 0
```

Trazabilidad completa (nada se pisa) **y** lectura O(1) del monto actual. El contrato, al cerrar,
hereda de `id_oferta_vigente`.

```
solicitud (monto_propuesto 5.000, inmutable)
   └─ oferta#1  origen=C  4.200  estado=C
        └─ oferta#2  origen=P  4.800  estado=C
             └─ oferta#3  origen=C  4.500  estado=A   ← monto_vigente = 4.500
```

## 6. WhatsApp: dos tablas, dos velocidades (D-10)

Un bot conversacional genera **mensajes** ("hola", "ok", "cuánto?"); un contacto comercial es un
**hecho de negocio**. Mapear 1 mensaje = 1 interacción llenaría de ruido la tabla que alimenta
reportes y modelos, y multiplicaría el volumen ~15×.

```
mensaje_conversacion   → log crudo. Alto volumen, append-only, retención acotada.
        │ (N mensajes destilan a…)
        ▼
contacto_comercial     → el hecho comercial. Bajo volumen, es lo que se consulta y reporta.
```

`mensaje_conversacion.id_contacto` es **nullable**: los mensajes de relleno quedan solo en el log;
cuando hay hecho comercial se crea **un** contacto y los mensajes que lo sustentan se ligan a él.
Trazabilidad conversacional completa sin contaminar el modelo de negocio — y la tabla que crece
rápido no es la que se consulta.

### 6.1 Número desconocido → cliente potencial automático (D-13)

**Redacción normativa**: *todo número de WhatsApp no reconocido generará automáticamente un cliente
potencial. El sistema continuará la atención sin requerir validación humana y ejecutará procesos
automáticos de resolución de identidad y deduplicación. Las coincidencias ambiguas se conservarán
como relaciones potenciales sin bloquear la operación ni generar tareas manuales.*

```
Mensaje entrante → normalizar número → buscar punto de contacto
   ├── Existe    → vincular conversación automáticamente
   └── No existe → crear cliente potencial automáticamente
```

El estado `NO_VERIFICADA` **no bloquea nada**: el bot puede conversar, calificar, registrar
necesidades, sugerir propiedades, programar visitas y ejecutar seguimientos.

**Deduplicación en segundo plano, sin tareas humanas:**

| Evidencia | Acción |
|---|---|
| Coincidencia exacta de teléfono, correo o documento | Vinculación automática |
| Coincidencia fuerte confirmada después | Unificación automática de identidad |
| Coincidencia ambigua | Se mantienen separados y se relacionan como `POSIBLE_MISMA_PERSONA` |

La fusión automática **solo** con evidencia determinística: mismo documento, correo verificado,
confirmación por código, número nuevo confirmado desde sesión autenticada, o identificador externo
inequívoco.

> ⚠️ **Encaje con Party-Role (a resolver antes de implementar)**: `TipoRol.CLIENTE` **ya existe** en
> el modelo v2. Un "cliente potencial" debe ser `persona` + `persona_rol(CLIENTE)` con
> `estado_identidad = NO_VERIFICADA`, **no una tabla `cliente_potencial` paralela**. Crear una tabla
> aparte reintroduciría la identidad fragmentada que V1 costó eliminar (MEJ-09/MEJ-10) y obligaría a
> fusionar dos modelos de identidad cuando el cliente se verifique.
>
> ⚠️ **`organizacion_id` implica multi-tenancy, que HOY NO EXISTE** en ninguna tabla del proyecto
> (verificado). Introducirlo afecta a todas las entidades, al alcance por rol (`Alcances`) y a cada
> query del paquete `query`. Es una decisión de arquitectura de producto, no un campo. Ver §12.
>
> ⚠️ **Consentimiento**: `persona.consentimiento_uso_dato` ya existe en el esquema. La creación
> automática por el bot debe registrar qué consentimiento aplica y cuándo se obtuvo (Ley 29733 de
> Protección de Datos Personales, Perú).

### 6.2 Retención de mensajes crudos (D-14)

**Redacción normativa**: *los mensajes crudos se conservarán durante 180 días y serán eliminados
automáticamente al vencer el periodo. Las interacciones, etiquetas, desenlaces y métricas derivadas
se conservarán como histórico operativo. Los mensajes seleccionados para entrenamiento deberán pasar
por sanitización, desidentificación y versionado en un repositorio separado de la base transaccional.*

| Nivel | Contenido | Retención |
|---|---|---|
| **Mensaje operativo** | texto original, adjuntos, audios, id del mensaje, datos del remitente | **180 días** |
| **Dato estructurado** | fecha, canal, dirección, interacción, etiquetas, intenciones, objeciones, resultado, tiempo de respuesta, estado comercial, confianza, modelo/prompt, validaciones | **Permanente** |
| **Corpus de entrenamiento** | mensajes sanitizados y desidentificados | Versionado, repositorio aparte |

Los 180 días permiten reconstruir conversaciones recientes, resolver incidentes, evaluar respuestas
del bot y corregir clasificadores, cubriendo ciclos comerciales largos — sin convertir el moat en
una acumulación ilimitada de conversaciones privadas.

Ejemplo de lo que sobrevive al vencimiento:

```
Mensaje eliminado: "El precio me parece muy alto, pero envíame los documentos."
Datos conservados: OBJECION_PRECIO · INTENCION_SOLICITA_DOCUMENTOS
                   sentimiento=INTERESADO_CON_OBJECION · confianza=0.94
                   resultado=CONTINUA_NEGOCIACION
```

**El entrenamiento nunca lee la tabla operativa**: un batch previo a la eliminación selecciona
conversaciones útiles → elimina nombres, teléfonos, correos, documentos y direcciones → control
automático de calidad → dataset versionado.

> 📌 **Esto corrige D-09 para esta tabla**: con retención por antigüedad, `mensaje_conversacion`
> conviene **particionarla por mes desde el día uno**, incluso a 200 usuarios. Purgar es entonces
> `DROP PARTITION` (instantáneo) en vez de un `DELETE` masivo mensual que hincha la tabla y obliga a
> `VACUUM`. Es la excepción justificada al "no particionar ahora" — y aplica solo a los mensajes,
> no a `contacto_comercial`.
>
> 📌 Audios y adjuntos no van en la BD sino en el almacén híbrido (`rest/almacen/`, S3-o-disco). El
> job de retención debe borrar **también los binarios**, no solo las filas.

## 7. Tareas que aprenden

`tarea` ya existe (v1) con `tipo`, `entidad_tipo`, `entidad_id`, `prioridad` y un motor de
recomendación por reglas. Para que evolucione a recomendación inteligente necesita capturar **si la
recomendación fue buena**:

```sql
-- añadir a tarea
origen        VARCHAR(10),   -- REGLA | MODELO | MANUAL
score         NUMERIC(4,3),  -- confianza de la recomendación
explicacion   VARCHAR(300),  -- POR QUÉ se recomendó (gobernanza + confianza del agente)
feedback      VARCHAR(12)    -- ACEPTADA | IGNORADA | RECHAZADA
```

Sin `feedback` el sistema recomienda para siempre y nunca aprende — el *agent washing* que el North
Star prohíbe. Con él, cada tarea recomendada es una fila de entrenamiento (*sugerí X → el agente lo
hizo → la operación cerró*), que es el bucle "ejecutar → acumular dato → inteligencia". Cuesta
4 columnas. `explicacion` es además lo que hace que un humano confíe en la sugerencia.

Evolución prevista: **reglas → scoring → modelo**, sin cambiar el esquema.

## 8. Estados: ordinal monótono (D-01, D-02)

Se descartó la pila: es LIFO y existe para volver atrás, que es justo lo que el negocio no hace.
El embudo es un **orden monótono** y se modela con un entero:

```
P=0  →  C=1  →  R=2  →  S=3  →  T=4          D = terminal
```

| Regla | Implementación | Costo |
|---|---|---|
| Avanzar o quedarse, nunca retroceder | `nivel_nuevo >= nivel_actual` | 1 comparación entera |
| Saltar directo (P → T) | `4 >= 0` ✓ | igual |
| Registrar sin avanzar | INSERT del contacto, `nivel` intacto | O(1) |
| Embudo / reportes | `WHERE nivel_avance >= 2` sobre índice | rango, no scan |

`nivel_avance SMALLINT` es además el campo caliente denormalizado: una sola columna sirve para la
regla **y** para los reportes.

> **Nota de paridad**: la v1 nunca emite el estado `E` de prospección (entregar propuesta deja `S`).
> Ver `contrato-congelado-f2-prospeccion-captacion.md` §2.

## 9. Escala: cuándo particionar (D-09)

| Escenario | Volumen estimado | Veredicto |
|---|---|---|
| **Hoy: 200 usuarios** | ~90K contactos/ciclo | **No particionar.** Un índice compuesto lo resuelve en ms |
| **Proyección: 100.000 usuarios** | ~60M contactos · ~900M mensajes | Particionar **por RANGE de fecha** |

El eje correcto a escala es **fecha, no contexto**: las consultas operativas son de datos recientes,
el archivado es por antigüedad, y el entrenamiento lee el histórico completo en batch. Partir por
`entidad_tipo` daría 5 particiones gigantes — poca ganancia. El contexto ya lo sirve el índice.
(Coincide con el diagnóstico de MEJ-15: los compuestos ya existían; el caso a favor de subtipar era
claridad y escala física, no índices faltantes.)

**Dos decisiones baratas de hoy evitan el rediseño de mañana:**
1. `fecha_hora NOT NULL` desde el día uno → futura columna de partición.
2. Mensajes separados de contactos → lo que crece 15× queda aislado.

Con eso, particionar después es trabajo de DBA (`ATTACH PARTITION`), no rediseño ni cambio de código.

⚠️ A 100K usuarios el cuello de botella **no será la tabla, será la ingesta** de webhooks (ráfagas →
cola/buffer). Particionar no resuelve eso; se aborda cuando llegue.

## 12. Preguntas abiertas

Las tres originales (identidad WhatsApp, retención, set de etiquetas) quedaron **resueltas** en
D-13/D-14/D-15. Las que abren esas decisiones:

1. **¿Multi-tenancy? (bloqueante)** — `organizacion_id` no existe hoy en ninguna tabla. Si ControlLocal
   va a servir a varias corredoras sobre una misma instancia, hay que decidirlo **antes** de escribir
   la migración, porque atraviesa todas las entidades, el `Alcances` por rol y cada query nativa.
   Si es una instancia por corredora, no se toca nada.
2. **`cliente_potencial` bajo Party-Role** — confirmar que se modela como `persona` +
   `persona_rol(CLIENTE)` + `estado_identidad`, y no como tabla paralela (§6.1).
3. **Familia RIESGO** — decidir si se recorta a `RIESGO_POSIBLE_FRAUDE` y el resto pasa a columnas de
   estado de `persona`/`solicitud` (§4.2). Afecta el rendimiento de las consultas de cartera.
4. **Umbral 0.60–0.79 y "acciones irreversibles"** — falta enumerar qué acciones concretas quedan
   vetadas en esa banda (¿agendar visita?, ¿enviar propuesta?, ¿crear oferta?).
5. **Modelo de sentimiento** — el ejemplo de §6.2 incluye `sentimiento=INTERESADO_CON_OBJECION`, que
   no está en el esquema propuesto. Definir si es una etiqueta más, una columna, o parte de `atributos`.
